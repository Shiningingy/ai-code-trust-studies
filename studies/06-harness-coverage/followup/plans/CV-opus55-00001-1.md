## What a near-miss means here

My earlier plan used "near-miss" loosely. Here is a precise definition.

**Three states per condition, not two.** For each person and each condition, the extraction records one of:
- **yes:** an accepted fact supports it.
- **no:** an accepted fact contradicts it, such as an inland employer, "no longer avoids dairy", or "drives to work".
- **unknown:** no accepted fact either way.

Telling "no" apart from "unknown" matters. "Unknown" is usually what an extraction miss looks like. "No" usually reflects something actually in the text.

**Definition.** A person is a near-miss if they are not already a match and either of these holds:
1. Exactly one condition is not "yes" (it is "no" or "unknown") and the other three are "yes".
2. All four are "yes" except c2 falls just short: exactly 2 distinct this-year events, or 3 or more only if a disputed mention is counted (lowercase ID, an event mentioned twice, or an unclear speaker).

People with two or more conditions short are not near-misses.

**How I'd find them.** I'd write the joined table to a TSV in the scratchpad, one row per P-ID with the four states and c2's distinct-event count. A short Python filter in Bash would list rows with exactly three "yes", plus the c2 = 2 rows. For each one, I'd Grep (`-i`, content mode) the person's full name, every alias, initial forms and P-ID. I'd then Read the surrounding passages to check the failing condition by hand.

## Where the near-miss check stops helping

The near-miss check only catches people whose facts my patterns mostly found. Suppose a qualifying person's employment and dairy facts are both written in phrasings I didn't anticipate ("is on staff at org 012", "has cut out milk and cheese"). That person shows up as 2/4 with two "unknown"s, and is never looked at again. Widening to "≥2 of 4" just moves the gap down a level. The real fix is to stop relying on my patterns' coverage and instead account for every relevant sentence.

## Revised plan

Steps 1 and 2 (identity table, org→city) stay the same. Steps 3 to 6 change as follows.

**3′. Two-tier extraction, broad and strict.**
- **Strict tier:** the precise patterns from the original plan. These decide yes/no.
- **Broad tier:** a deliberately loose, case-insensitive topic vocabulary for each condition:
  - c1: `work|employ|job|staff|hired|org(anization)?\s*\d`
  - c2: `volunteer|helped|pitched in|event-`
  - c3: `dairy|milk|cheese|lactose|vegan|butter|yogurt`
  - c4: `bus|train|transit|subway|metro|tram|ferry|commut|rides?|drive|car|bike`

  A Python script, run via Bash, splits passages into sentences, protecting "St." and initials like "E.". It tags every sentence that hits any broad term, writes `broad.tsv` to the scratchpad, and records whether the strict tier accepted, rejected (with a reason), or didn't match each one.

**3″. Read the residual.** The sentences that hit the broad tier but not the strict tier are where missed facts hide. I'd read all of them, not a sample, using Read on the scratchpad file in chunks. For each one I'd either add it as a fact (and widen the strict pattern if it reveals a new phrasing, then rerun) or mark it irrelevant ("bus stop renovation", "dairy farm tour"). That way every topical sentence in the file gets a decision, instead of only the ones my patterns anticipated.

**4′. Attribution coverage.** The script also writes out every accepted or residual fact it couldn't assign to a P-ID: pronouns, "the quoted speaker", unmapped initials. I'd read each in context with Read at the passage offset. Anything still unassignable stays unassigned, but gets listed so I know how many there are.

**5′. Person dossiers for anyone with partial evidence.** I'd take every person with at least one "yes" from the strict tier or the reviewed residual. For each "unknown" condition, I'd Grep their names and aliases and read every hit, not just near-misses. Because of the residual step, a person whose facts were all missed by the strict tier still reaches this point.

**6′. Sanity checks.**
- Compare per-condition "yes" counts against raw Grep counts of key phrases. A large gap points to a missed phrasing.
- Spot-read a few random passages that hit no broad term, to confirm the vocabulary isn't missing a whole style of phrasing.

**Fallback.** If the residual is huge, or the spot-reads turn up missed phrasings, I'd read the whole file sequentially with Read. It's about 469 KB, roughly 120k tokens. That is expensive, so it's a last resort rather than the default.

## Rough added cost

- **Original plan:** about 15–25 tool calls, mostly Grep/Bash, plus targeted Read of a few candidates' passages.
- **The revision adds:**
  - one more script pass with a negligible runtime;
  - reading the residual, likely a few hundred sentences or about 20–60 KB (roughly 5–15k tokens across 5–15 Read calls);
  - dossiers for maybe 20–60 people instead of a handful (another 20–40 Grep/Read calls).

Overall that's about 1.5–2.5× the original effort. Hitting the full-read fallback would add about 120k tokens more. The gain is that the result no longer depends on my patterns anticipating every phrasing.
