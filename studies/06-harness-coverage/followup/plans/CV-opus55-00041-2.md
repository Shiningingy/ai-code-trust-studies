## What a near-miss means for this query

My earlier plan used "met four of the five" loosely. Here is the precise version.

**Definition.** For each person (P-ID), my strict patterns give each condition one of three outcomes:

- **pass**: a positive fact was found.
- **decoy-only**: only near-miss wording was found, such as `old-event`, "emergency contact" or "temporarily skipping milk".
- **absent**: nothing was found.

A near-miss is a person who passes **exactly 4 of the 5 conditions** and fails one, whether that one is decoy-only or absent. c1 is a count, so it gets one extra case: a person with **exactly 2 distinct this-year events** who passes c2–c5 is also a near-miss. c2 is a join, so a person with a guardian fact whose youth has no confirmed current evening course, or the reverse, counts as failing c2 by one step.

**How I'd find them.** I'd use Bash (awk/grep, with scripts saved to the scratchpad) to write a table of P-ID × condition → pass/decoy/absent, plus the c1 event count. Then I'd filter for a score of 4, or c1 = 2 with the other four passing. For each near-miss, I'd Grep every alias of that person with context and Read the passages, looking for the missing fact or for a negation that should cancel one of the passes.

**Its limit.** This check only helps when the patterns miss **one** fact for someone. Suppose a real match uses unexpected wording for two or three conditions, for example "rail" instead of "train", "steers clear of dairy", or a fruit I didn't list. That person scores 2 or 3, looks like noise, and is never reviewed. So the near-miss check is a sanity test. It doesn't guarantee recall.

## What I'd do instead: checks that don't rely on my patterns

The fix is to stop measuring recall against my own patterns. Instead I'd (a) make sure every sentence in the file gets a label and (b) review a loose superset of possible matches, built from loose matching instead of the strict patterns.

**A. Template census (finds wording I didn't think of).** The passages look machine-generated, so the number of distinct sentence shapes should be small.
- With Bash/sed, split passages into clauses. Then replace every alias with `<P>`, youth tokens with `<Y>`, event tokens with `<E>`, quoted "I" with `<I>`, and the object of eating, buying or avoiding with `<FOOD>`.
- Run `sort | uniq -c` to get the distinct skeletons. Read the whole list and label each skeleton as positive for cN, decoy for cN, negation or correction, or irrelevant.
- Any skeleton I haven't labelled blocks the final answer. Every clause in the file then has a reviewed label, so unexpected wording can't slip through, however many conditions it affects.
- Separately, use `grep -o` to list every distinct `<FOOD>` value and every course name, and classify each by hand. That fixes the fixed fruit list and the `evening_*` assumption.

**B. Loose superset review (catches people the strict patterns under-score).** Using the broad vocabulary from A (every keyword from positive and decoy skeletons), mark a person "touched" for condition N if *any* clause about them mentions that condition's topic. Wording doesn't matter at this stage. Any real match must be touched on all five, so:
- Build the set of people touched on all 5. For c1, require at least 3 distinct event mentions, ignoring whether they say this year or last year. This set contains every true match, provided name resolution works.
- Write each of these people's clauses, including quotes attributed to them, to a dossier file in the scratchpad, and Read each dossier completely. That's where I'd decide each condition and catch negations or later corrections.
- Their scores under the strict patterns become a cross-check: any person whose dossier verdict differs from the pattern verdict points to a pattern bug, and I'd fix it and rerun.

**C. Name coverage (catches facts filed under no one).** A missed alias causes misses across several conditions at once. I'd Grep for every capitalised full-name shape, every initial-plus-surname shape, and their lowercase versions, then diff the results against the roster table. Every unresolved mention gets read and either mapped to an ID, marked ambiguous, or confirmed as having no roster entry. Clauses with a condition keyword but no resolved subject also get read, since that is where a fact can end up assigned to nobody.

## Revised plan

1. Build the identity table, as before. Then run **C** and fix the gaps before going further.
2. Run the **A** template census and label every skeleton. Write the strict extraction rules from those labels instead of from my guessed wording.
3. Extract facts per condition and join on P-ID, as before. Normalise youth tokens for c2.
4. Run the **B** loose superset review and read every dossier. Settle any disagreement with the strict results by fixing the rules and rerunning.
5. Run the near-miss check (4 of 5, or c1 = 2) as a final consistency test. After A and B it should turn up nothing new. If it does, that means a bug.
6. For each final match, read the passage that proves each condition. Output `{"matches": [...]}` with IDs sorted, and list separately anyone left out because they have no roster ID or an ambiguous alias.

## Rough cost

- **Template census:** about 3–5 extra Bash calls, plus reading the skeleton list. With templated text I'd expect somewhere between tens and a few hundred skeletons, so roughly 15–40k tokens. If the text turns out much less templated, the cost goes up a lot, and I'd fall back to reviewing only the keyword hits that weren't classified.
- **Superset dossiers:** a few Bash calls plus one Read per candidate. If 10–40 people are touched on all five conditions, at about 1–2k tokens each, that's roughly 20–60k tokens.
- **Name coverage:** 1–3 Grep/Bash calls and a short manual review.

Overall, I'd expect this to roughly double the tool calls and tokens of the original plan, maybe 1.5–2.5×. In exchange, recall rests on every clause being labelled and every possible match being read, not on my guesses about wording.
