## What a near-miss means here

A near-miss is a person my extraction says fails the query, but only barely. This is the person most likely to be a real match hidden by an extraction error. The near-miss check tests my patterns, not the people. If one template misses one valid wording, the people it hurts will show up as passing 4 of 5.

**Precise definition.** For each ID and each condition, I'd record one of four states, not just pass/fail:

- **PASS:** a positive fact matched a strict template, and no later correction overrides it.
- **FAIL-DECOY:** only decoy wordings matched. Examples: last-year events, "emergency contact, but not a guardian", a train choice forced by disruption, "used to enjoy", temporary skipping.
- **FAIL-ABSENT:** no sentence about this person matched anything for this condition.
- **PARTIAL:** the condition depends on a count or a join, and it got partway. Examples: c1 with exactly 2 distinct this-year events, or c2 where the person is a guardian but the youth has no evening-course record (or a conflicting one).

A **near-miss** is any ID with 4 PASS and 1 non-PASS. I'd look hardest at the non-PASS states in this order: FAIL-ABSENT, then PARTIAL, then FAIL-DECOY. Absent and partial are where pattern gaps hide (an unfamiliar phrasing, an unresolved alias, a youth ID format I didn't normalize). A decoy failure means I read a sentence and judged it, so it's less likely to be an error, but I'd still re-read the decoy sentence.

**How to find them.** A Python script (run via Bash, saved in the scratchpad) would print the 160×5 state matrix. I'd filter for 4 PASS, and for each near-miss print every passage that mentions any of the person's names or aliases. I'd read those by hand, using Grep or Read to jump to passages.

## When the near-miss check isn't enough

If my patterns miss facts for two or more of a real match's conditions, that person passes only 3 of 5 or fewer. They then sit among dozens of genuine non-matches, and the 4-of-5 filter never shows them to me. Lowering the threshold to 3 or 2 doesn't fix this. It grows the hand-read list toward all 160 people and still relies on the same patterns.

The fix is to measure coverage per sentence, not per person. If every relevant sentence in the file is either matched by a template or read by me, a person can't lose facts silently, no matter how many conditions are affected.

## Revised plan

**1. Identity map** (unchanged). Pull every roster line with a regex, match without regard to case, and check that each alias maps to exactly one ID.

**2. Strict extraction** (unchanged). Use the templates with polarity, split into clauses, count distinct events, and normalize youth IDs before the join.

**3. New: inventory of sentence shapes.** A script would replace each sentence's resolved names, P-IDs, youth IDs, event IDs, course names, food words and years with placeholders like `<PERSON>` and `<EVENT>`. It would then group sentences by the resulting shape and count each group. The file is generated from templates, so 2,327 passages should reduce to a manageable number of shapes, probably low hundreds.

I'd mark every shape as one of: a strict positive for some condition, a known decoy, or irrelevant. Any unmarked shape gets read once by hand. This catches unfamiliar wordings directly, including ones with no obvious keyword ("signed up to staff", "takes the rail", "is responsible for Y042"). It also exposes leftover proper nouns that didn't resolve to an ID, which means an alias gap.

**4. New: a loose superset check.** For each person and condition, a loose rule passes if any sentence that mentions them contains a broad keyword:

- c1: volunteer / helped / staffed / event
- c2: guardian / youth / Y-ID / ward
- c3: train / rail / plane / fly / flight
- c4: any food word / eat / taste
- c5: dairy / milk / cheese / yogurt / lactose / vegan

For c1, the loose rule counts any event ID without filtering by year. I'd then hand-read everyone who passes all five loosely but not all five strictly. The loose set must contain the strict set, so a script assertion would flag any strict match that fails loosely as a bug.

**5. New: sentences without a resolved name.** I'd list every sentence that contains a condition keyword but no resolved person. These can be pronoun or "the same volunteer" continuations, first-person lines inside quotes, or alias misses. I'd resolve each one by reading the surrounding passage.

**6. Near-miss audit** (step 5 of the old plan, now defined above). I'd run it on the 4-of-5 PASS list.

**7. Combine and verify.** I'd re-read the supporting passages for every finalist and then output the sorted JSON. The finished check would be: no unmarked shapes, no unresolved keyword sentences, the loose set contains the strict set, and every near-miss has been explained.

## Added cost

- **Shape inventory:** one more script and one or two Bash runs. Most of the cost is reading the shape list, perhaps 100–300 lines, which is roughly 15–30K tokens. This is the biggest addition, but it only happens once and its size depends on the number of shapes, not passages.
- **Loose superset check:** a few lines added to the same script. Hand reading is probably 5–30 people at about 5–15 short passages each, so roughly 10–30K tokens.
- **Unresolved-sentence list:** cheap to produce, with likely a few dozen sentences to read.

Overall, this is about 5–10 more tool calls and roughly 2–3× the reading of the original plan. That stays bounded because the passages are short and the shape grouping shrinks most of the file into a few hundred templates.
